# Mini Payment System — Development Plan

Pet project: a small payment system with deposits and two-phase withdrawals, built with **Java 25 + Spring Boot 4.1**, using **H2** (schema generated from entities) and deployed on **Fly.io**.

The API is plain hand-written Java: `@RestController`s, DTOs as records, and a hand-written `RestClient` for the vendor. No OpenAPI/YAML contracts and no database migrations for now. Both are listed as optional upgrades at the end.

Each milestone has a goal, implementation details and a "Done" criterion. A milestone is finished only when its "Done" criterion is met.

---

## 0. Overview

### End-to-end flow

1. Client reports a deposit of 1000 → payment api fetches it from the vendor API → `DEPOSIT 1000`. Balance 1000, available 1000.
2. Client creates a withdrawal of 100 → `CREATED`, client gets an id, balance not touched yet.
3. Worker: funds available → `HOLD 100` (available 900) → creates the payment at the vendor → confirms it.
4. Vendor confirms → `SETTLE 100`. Balance 900, available 900.

Failure paths:

- Not enough funds at the hold step → `DECLINED`, no hold.
- Vendor rejects → `RELEASE 100`, available back to 1000, `DECLINED`.

### Tech stack

| Area                 | Choice                                                                 |
| -------------------- | ---------------------------------------------------------------------- |
| Language / framework | Java 25, Spring Boot 4.1, Gradle (Kotlin DSL)                          |
| Database             | H2, file mode on a Fly volume; in-memory in tests                      |
| Schema               | Generated by Hibernate from `@Entity` classes                          |
| Persistence          | Spring Data JPA, optimistic locking (`@Version`)                       |
| API                  | Hand-written `@RestController`s, DTOs as Java records, Bean Validation |
| HTTP client          | Hand-written `RestClient` behind a `VendorGateway` interface           |
| Resilience           | Resilience4j (retry + rate limiter)                                    |
| Security             | Spring Security, HTTP Basic, separate chain for webhooks               |
| Tests                | JUnit 5, AssertJ, MockMvc                                              |
| CI/CD                | GitHub Actions → `flyctl deploy`                                       |

```
├── vendor-api/                    # shared DTO records for the vendor HTTP API
│   └── src/main/java/.../vendor/api/
```

`vendor-api` is a tiny plain-Java module (records only, no Spring). Both `payment` (client side) and `mock-vendor` (server side) depend on it. This keeps the main benefit the YAML contract gave you: the two apps can't drift apart, because they compile against the same classes.

### Fly topology

```
                 internet (HTTPS, Basic auth)
                          │
                ┌─────────▼─────────┐
                │  payment (app)   │── H2 file on Fly volume (/data)
                └─────────┬─────────┘
                          │ Fly private network (6PN)
                ┌─────────▼─────────┐
                │ mock-vendor (app) │   no public IP, in-memory state
                └───────────────────┘
```

### Conscious simplifications

- **One user:** login and password come from config. There's no registration.
- **One payment table, one vendor:** real systems split these into separate services.
- **Ledger without double-entry:** one row per movement, with a type.
- **H2 file DB:** no database server and no migrations. The cost is **exactly one `payment` machine**, a short downtime on each deploy, and resetting the DB when the entity model changes incompatibly.
- **No API contract files:** the code is the contract.

## Milestone 2 — REST API

**Goal:** all endpoints exist as hand-written controllers with typed DTOs and validation. Endpoints return `501 Not Implemented` for now.

### Payment API

| Method | Path                | Request                                | Response                                 |
| ------ | ------------------- | -------------------------------------- | ---------------------------------------- |
| `POST` | `/deposits`         | `{ vendorPaymentId }`                  | `201 PaymentResponse` (`200` on repeat)  |
| `GET`  | `/accounts/me`      | —                                      | `{ balance, held, available, currency }` |
| `POST` | `/withdrawals`      | `{ idempotencyKey, amount, currency }` | `201 PaymentResponse` (`200` on replay)  |
| `GET`  | `/withdrawals/{id}` | —                                      | `PaymentResponse`                        |

Amounts are `long` in minor units (cents) everywhere, which avoids decimal issues.

### Tasks

1. **DTOs as records** with Bean Validation:

   ```java
   public record CreateWithdrawalRequest(
           @NotBlank @Size(min = 8, max = 64) String idempotencyKey,
           @Positive long amount,
           @NotBlank @Size(min = 3, max = 3) String currency) {}

   public record PaymentResponse(UUID id, PaymentType type, String status,
                                 long amount, String currency, Instant createdAt) {}

   public record AccountResponse(long balance, long held, long available, String currency) {}

   public record RegisterDepositRequest(@NotBlank String vendorPaymentId) {}
   ```

   Never return entities from controllers. Map them to records (a small static `from(entity)` method is enough).

2. **Controllers** — thin: accept the request, call the service, return the response.

   ```java
   @RestController
   @RequestMapping("/withdrawals")
   class WithdrawalController {
       @PostMapping
       ResponseEntity<PaymentResponse> create(@Valid @RequestBody CreateWithdrawalRequest req) {
           throw new ResponseStatusException(HttpStatus.NOT_IMPLEMENTED);
       }
       @GetMapping("/{id}")
       PaymentResponse get(@PathVariable UUID id) {
           throw new ResponseStatusException(HttpStatus.NOT_IMPLEMENTED);
       }
   }
   ```

3. **Error handling** — a `@RestControllerAdvice` that returns `ProblemDetail` (RFC 9457) for:
   - validation errors → `400`
   - not found → `404`
   - idempotency conflict → `409`
   - illegal state transition → `409`

   Also set `spring.mvc.problemdetails.enabled: true`.

4. **Vendor API records** in the `vendor-api` module:

   ```java

   public record VendorPayment(String id, UUID reference, VendorPaymentType type,

   public enum VendorPaymentStatus { CREATED, COMPLETED, REJECTED }
   ```

   Also put the paths in a constants class there, for example `VendorPaths.PAYMENT = "/payment"`, so both sides use the same strings.

5. **Tests** — `@SpringBootTest` + `@AutoConfigureMockMvc`:
   - no credentials → `401`
   - valid credentials → `501`
   - invalid body (negative amount) with credentials → `400`

## Milestone 3 — Domain, ledger, state machine, tests

**Goal:** accounts, ledger and the withdrawal state machine are implemented in the service layer, with three green tests.

### Entities (the schema comes from these)

Constraints are declared on the entities so Hibernate creates them in H2. The unique constraints are the database-level money protection.

```java
@Entity
@Check(constraints = "balance >= 0 AND held >= 0 AND held <= balance")
public class Account {
    @Id @GeneratedValue Long id;
    @Column(nullable = false, unique = true) String owner;
    @Column(nullable = false, length = 3) String currency;
    @Column(nullable = false) long balance;
    @Column(nullable = false) long held;
    @Version long version;

    public long available() { return balance - held; }
}

@Entity
@Table(uniqueConstraints = {
    @UniqueConstraint(name = "uq_client_idempotency_key", columnNames = "client_idempotency_key"),
    @UniqueConstraint(name = "uq_vendor_payment_id",      columnNames = "vendor_payment_id")
}, indexes = @Index(name = "ix_payment_status_due", columnList = "status, next_attempt_at"))
public class Payment {
    @Id UUID id;                                   // generated in code: UUID.randomUUID()
    @ManyToOne(optional = false) Account account;
    @Enumerated(EnumType.STRING) @Column(nullable = false) PaymentType type;
    @Enumerated(EnumType.STRING) @Column(nullable = false) WithdrawalStatus status;
    @Column(nullable = false) long amount;
    @Column(nullable = false, length = 3) String currency;
    @Column(name = "client_idempotency_key") String clientIdempotencyKey;
    @Column(name = "vendor_payment_id") String vendorPaymentId;
    int attempts;
    @Column(name = "next_attempt_at", nullable = false) Instant nextAttemptAt;
    String lastError;
    @Column(nullable = false) Instant createdAt;
    Instant updatedAt;
    @Version long version;
}

@Entity
@Table(uniqueConstraints = @UniqueConstraint(
    name = "uq_payment_entry", columnNames = {"payment_id", "entry_type"}))
public class LedgerEntry {
    @Id @GeneratedValue Long id;
    @ManyToOne(optional = false) Account account;
    @ManyToOne(optional = false) @JoinColumn(name = "payment_id") Payment payment;
    @Enumerated(EnumType.STRING) @Column(name = "entry_type", nullable = false) LedgerEntryType entryType;
    @Column(nullable = false) long amount;
    @Column(nullable = false) Instant createdAt;
}
```

Notes:

- `@Check` (Hibernate annotation) adds a `CHECK` constraint. Even buggy code can't drive the balance negative.
- H2 treats `NULL`s as distinct in unique constraints. Deposits without an idempotency key, and withdrawals without a vendor id yet, won't collide.
- `LedgerEntry` is append-only: there are no setters, and the code never updates or deletes it.
- Deposits reuse `Payment` with `type = DEPOSIT` and status `COMPLETED`. If you prefer, use a separate `DepositStatus` enum or a plain `String` status column with type-specific logic.
- Seed the single account at startup with an `ApplicationRunner`: create `demo/USD` if it doesn't exist.
- `ddl-auto=update` adds new columns and tables but won't rename or drop anything. After an incompatible entity change, delete the H2 file (locally, `rm -rf data/`; on Fly, SSH in and delete `/data/payment*`, or recreate the volume).

### State machine

```java
public enum WithdrawalStatus {
    CREATED, HELD, INITIATED, COMPLETED, DECLINED;

    private static final Map<WithdrawalStatus, Set<WithdrawalStatus>> ALLOWED = Map.of(
        CREATED,   Set.of(HELD, DECLINED),
        HELD,      Set.of(INITIATED, DECLINED),
        INITIATED, Set.of(COMPLETED, DECLINED),
        COMPLETED, Set.of(),
        DECLINED,  Set.of()
    );

    public boolean canMoveTo(WithdrawalStatus next) { return ALLOWED.get(this).contains(next); }
    public boolean isTerminal() { return ALLOWED.get(this).isEmpty(); }
}
```

- Exactly **one** method changes the status: `Payment.transitionTo(next)`. It throws `IllegalStateTransitionException` if the move isn't allowed, and there's no public setter for `status`.
- `COMPLETED` and `DECLINED` are terminal: once reached, the payment never changes again.

### AccountService: the only place money moves

All methods are `@Transactional`. Each one writes the ledger entry and updates the account in the same transaction.

| Method             | Ledger    | Account change                                                                       |
| ------------------ | --------- | ------------------------------------------------------------------------------------ |
| `deposit(payment)` | `DEPOSIT` | `balance += amount`                                                                  |
| `hold(payment)`    | `HOLD`    | `held += amount` (requires `available >= amount`, else `InsufficientFundsException`) |
| `settle(payment)`  | `SETTLE`  | `balance -= amount`, `held -= amount`                                                |
| `release(payment)` | `RELEASE` | `held -= amount`                                                                     |

- On an optimistic lock conflict (`ObjectOptimisticLockingFailureException`), retry the whole transaction up to about 3 times. Do the retry in the caller (a small loop or `@Retryable`), never inside the transaction.
- `uq_payment_entry` makes every step idempotent at the database level: a second `HOLD` for the same payment fails instead of double-holding.

### Endpoints wired

- `GET /accounts/me` → reads the account and returns `available = balance - held`.
- `GET /withdrawals/{id}` → reads the payment and returns `404` if it's missing or not a withdrawal.
- `POST /withdrawals` → creates a `CREATED` payment. Idempotency comes in Milestone 4.

### Tests

1. **Hold/settle/release math:** deposit 1000 → hold 100 → available 900 → settle → balance 900, available 900. Separate case: hold → release → available back to 1000.
2. **State machine:** a plain unit test of every allowed and forbidden transition. Terminal states reject everything.
3. **Concurrency:** with 1000 on the account, 20 threads each try to hold 100 at the same time (`ExecutorService` + `CountDownLatch`, with the retry wrapper on). Expect:
   - exactly 10 holds succeed and the rest fail with insufficient funds
   - `held = 1000`
   - the ledger has exactly 10 `HOLD` rows

   Don't put `@Transactional` on this test class, or all threads would share one transaction context. Clean up with `@AfterEach`/`@Sql` instead.

**Done:** the three tests are green in CI.

## Milestone 4 — Idempotency key

**Goal:** two `POST /withdrawals` with the same key produce one withdrawal and the same response.

### Implementation

1. `idempotencyKey` is required in the body; it's already validated in Milestone 2.
2. Flow in `WithdrawalService.create(request)`:

   ```
   1. look up by clientIdempotencyKey → found? return it (200)
   2. new transaction: save a new payment (status CREATED) → return it (201)
   3. on DataIntegrityViolationException (uq_client_idempotency_key):
        new transaction: load by key → return it (200)
   ```

   - Use `saveAndFlush` so the constraint fires inside `create`, not later at commit time.
   - steps 2 and 3 each runs in its own transaction. H2 is more forgiving here than Postgres, but this way the code stays correct if you switch databases later.
   - The service returns a small result, `record CreateResult(Payment payment, boolean created)`, so the controller can choose `201` or `200`.

3. **Same key, different body** (different amount or currency) → `409 Conflict`. Compare the stored payment with the request before returning it.
4. The key is global because there's a single user. With many users it would be `UNIQUE (account_id, client_idempotency_key)`.

### Why both checks

When two requests with the same key arrive at the same moment, the lookup in step 1 finds nothing for either of them. The unique constraint lets only one insert through. The other gets the exception and returns the first payment.

### Tests

- Sequential: same key twice → same id, second response `200`, one row in the database.
- Concurrent: 10 threads with the same key at once → all get the same id, exactly one row.
- Same key, different amount → `409`.

**Done:** two requests with one key produce one withdrawal, including when sent concurrently.

## Milestone 5 — Vendor, retries, worker

**Goal:** a withdrawal goes all the way to `COMPLETED` through the mock vendor, and survives vendor outages and app restarts.

### 5.1 mock-vendor app

- Hand-written `@RestController`s using the shared `vendor-api` records:
  - `POST /payment` (body `CreatePayoutRequest`): if `reference` already exists, return the existing payment (idempotent create). Otherwise create it with status `CREATED`.
  - `POST /payment/{id}/confirm`: `CREATED` → `COMPLETED` (or `REJECTED`, depending on the chaos mode). If already terminal, return it unchanged.
  - `GET /payment/{id}`: return the payment, used for deposits.
- Storage: an in-memory `ConcurrentHashMap` indexed by `id` and by `reference`. It's a mock, so losing data on restart is fine.

### 5.2 VendorGateway

```java
public interface VendorGateway {
    VendorPayment createPayout(UUID reference, long amount, String currency);
    VendorPayment confirm(String vendorPaymentId);
    VendorPayment get(String vendorPaymentId);
}
```

- `HttpVendorGateway` uses a `RestClient` built from `RestClient.Builder` with `baseUrl(vendorBaseUrl)`:
  ```java
  VendorPayment createPayout(UUID ref, long amount, String currency) {
      return restClient.post().uri(VendorPaths.PAYMENT)
          .body(new CreatePayoutRequest(ref, amount, currency))
          .retrieve()
          .onStatus(HttpStatusCode::is5xxServerError, (req, res) -> { throw new VendorUnavailableException(...); })
          .onStatus(s -> s.value() == 422, (req, res) -> { throw new VendorRejectedException(...); })
          .body(VendorPayment.class);
  }
  ```
  Also catch `ResourceAccessException` (timeouts, connection refused) and turn it into `VendorUnavailableException`.
- `FakeVendorGateway` in tests, with scriptable responses: success, reject, unavailable N times.
- Error categories:
  - `VendorUnavailableException`: retryable.
  - `VendorRejectedException`: a definitive business rejection, not retryable.
  - Other 4xx responses: a bug. Store it in `lastError` and log it.
- Timeouts: connect 2s, read 5s, configured on the request factory (`JdkClientHttpRequestFactory` or `SimpleClientHttpRequestFactory`).

### 5.3 Fast retries and rate limit (Resilience4j)

```yaml
resilience4j:
  retry.instances.vendor:
    max-attempts: 3
    wait-duration: 200ms
    retry-exceptions: [com.example.payment.vendor.VendorUnavailableException]
  ratelimiter.instances.vendor:
    limit-for-period: 10
    limit-refresh-period: 1m
    timeout-duration: 0 # don't block the worker; treat a refusal as "try later"
```

- Decorate each gateway call with the `RateLimiter` on the outside and the `Retry` inside, so every retry also uses a permit ("retries count too"). Programmatic decoration (`Decorators.ofSupplier(...)`) makes this order explicit. With annotations, check the aspect order.
- Only idempotent calls are retried. Both vendor calls are idempotent by design: `reference` on create, and confirm is a no-op on repeat.
- With a single `payment` machine, the per-JVM rate limiter really does mean 10 requests per minute to the vendor.

### 5.4 Worker

- `@Scheduled(fixedDelay = 1000)` in `WithdrawalWorker`, with `@EnableScheduling` on a config class.
- Each tick, pick due withdrawals:
  ```java
  List<Payment> due = repo.findTop10ByTypeAndStatusInAndNextAttemptAtBeforeOrderByNextAttemptAt(
      WITHDRAWAL, List.of(CREATED, HELD, INITIATED), Instant.now());
  ```
- Only one machine and one scheduler thread run, so no row-claiming or locking is needed. `@Version` on `Payment` still catches a race with an API request.
- Each payment advances **one step per tick**. A step makes **at most one vendor call**, always **outside** any DB transaction, and its result is saved right after in **one** transaction:

  | Status      | Step                                          | On success (one transaction)          | On failure                                                                                                           |
  | ----------- | --------------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
  | `CREATED`   | `AccountService.hold`                         | `HOLD`, → `HELD`                      | insufficient funds → `DECLINED`, no hold                                                                             |
  | `HELD`      | `vendor.createPayout(reference = payment.id)` | save `vendorPaymentId`, → `INITIATED` | unavailable → `attempts++`, back off; after **5** attempts → `RELEASE`, `DECLINED`. Rejected → `RELEASE`, `DECLINED` |
  | `INITIATED` | `vendor.confirm(vendorPaymentId)`             | `SETTLE`, → `COMPLETED`               | unavailable → retry **without limit**, with capped back-off. Rejected → `RELEASE`, `DECLINED`                        |

- Back-off: `nextAttemptAt = now + min(2^attempts × 1s, 10 min)`, plus a little jitter. When the rate limiter refuses, reschedule a few seconds later without incrementing `attempts`.
- One payment's failure must not stop the loop: wrap each payment in try/catch and log.
- **Crash between the vendor call and the DB save:** the status is still `HELD`, so the next tick calls `createPayout` again with the same reference. The vendor returns the existing payment and we save it. Nothing is lost or duplicated.
- **No giving up after `INITIATED`:** the money may already be moving at the vendor. Releasing the hold could let the client spend it twice, so only the hold is ever cancelled.

### 5.5 Deposits (real implementation)

`POST /deposits { vendorPaymentId }`:

1. Call `vendor.get(vendorPaymentId)`, outside a transaction.
2. Check `type = PAYIN`, `status = COMPLETED`, and that the currency matches the account.
3. In one transaction: insert a `Payment` (type `DEPOSIT`, status `COMPLETED`, `vendorPaymentId`) and call `AccountService.deposit`.
4. If `uq_vendor_payment_id` is violated, load the existing deposit in a new transaction and return it (`200`). The same deposit is never credited twice.

### 5.6 Observability (light)

- Log every transition, for example `payment=<id> HELD -> INITIATED attempts=1`.
- `fly logs` is enough for this project.

### Tests

- **Happy path** with `FakeVendorGateway`: deposit 1000 → withdraw 100 → call `worker.tick()` directly a few times → `COMPLETED`, balance 900. The ledger has `DEPOSIT`, `HOLD`, `SETTLE`. Disable the scheduler in tests with `@Profile` or a property, and drive ticks by hand.
- **Insufficient funds** → `DECLINED`, no `HOLD` entry.
- **Vendor down during create**, 5 times → `RELEASE`, `DECLINED`, available back to the full amount.
- **Vendor down during confirm** 20 times, then back up → eventually `COMPLETED`.
- **Vendor rejects on confirm** → `RELEASE`, `DECLINED`.
- **Crash simulation:** the fake gateway succeeds on create but the save throws → next tick → exactly one vendor payment, status `INITIATED`.
- **Smoke test on Fly** (a `curl` script):
  1. Create a deposit via `/admin/deposits` (run with `fly ssh console` on `mock-vendor`, or temporarily expose it) and report it.
  2. Withdraw, then poll until `COMPLETED`.
  3. Repeat with chaos `DOWN` for a minute, then `OK`.
  4. Repeat with `fly machine restart` in the middle of a withdrawal.

**Done:** a withdrawal reaches `COMPLETED` on Fly, and survives a vendor outage and an app restart mid-flow.

## Optional upgrades

### A. Deposit webhook with HMAC signature

1. After `POST /admin/deposits`, mock-vendor sends `POST /webhooks/vendor` to payments with body `{ vendorPaymentId }` and these headers:
   - `X-Signature: hex(HMAC-SHA256(secret, timestamp + "." + rawBody))`
   - `X-Timestamp: <epoch seconds>`
2. In payments, a filter in the webhook security chain:
   - reads the raw body bytes once and re-exposes them through a request wrapper
   - recomputes the HMAC and compares with `MessageDigest.isEqual` (constant time)
   - rejects timestamps older than 5 minutes, which prevents replays
   - returns `401` for a bad signature
3. The handler calls the same `DepositService.register(vendorPaymentId)` as `POST /deposits`, so it still fetches the deposit from the vendor API. The webhook only says "go look", and `uq_vendor_payment_id` handles duplicates.
4. Both apps share one secret: `fly secrets set WEBHOOK_SECRET=...`.
5. Tests:
   - valid signature → `200`, deposit recorded
   - tampered body → `401`
   - old timestamp → `401`
   - same webhook twice → one deposit

### B. PostgreSQL + Flyway

When you outgrow one machine or want safe schema changes:

- Add Fly Postgres. Set `SPRING_DATASOURCE_URL` as `jdbc:postgresql://...`, because Fly's `DATABASE_URL` uses `postgres://`, which JDBC doesn't accept.
- Generate a baseline `V1__init.sql` from the current H2 schema, add `spring-boot-starter-flyway` + `flyway-database-postgresql`, and switch to `ddl-auto=validate`.
- Use Testcontainers Postgres in tests.
- With several machines, the worker needs to claim rows (`FOR UPDATE SKIP LOCKED` plus a lease column) and to run as a single active worker (`pg_try_advisory_lock`), which keeps the global vendor rate limit correct.
- Remove the Fly volume and the `count 1` restriction.

### C. Spec-first API (OpenAPI)

- Option 1 (code-first, cheap): add `springdoc-openapi` to get a generated spec and Swagger UI from the existing controllers.
- Option 2 (spec-first): write `payment-api.yaml` and `vendor-api.yaml` and generate interfaces with `openapi-generator`. This would replace the `vendor-api` records module.
